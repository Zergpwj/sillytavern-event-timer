# 酒馆接入笔记（已在真实源码中核对）

本文件记录本项目实际依赖的 SillyTavern 接口事实。
**所有结论都是从酒馆官方源码里读出来并核对过的**，不是从博客或其它扩展里抄的。
没核对过的地方会明确标注。

核对用的分支：`release` 与 `staging`（用于交叉验证接口稳定性）。

## 1. `globalThis.SillyTavern`

`public/script.js:293`：

```js
// API OBJECT FOR EXTERNAL WIRING
globalThis.SillyTavern = {
    libs,
    getContext,
};
```

这是酒馆官方给外部代码留的**唯一稳定入口**。它暴露 `getContext()`，
返回一个包含几乎所有常用能力的大对象。

**强烈建议只用它，不要 `import` 酒馆源码。**
很多现存扩展写：

```js
import { extension_settings } from '../../../extensions.js';
import { setExtensionPrompt } from '../../../../script.js';
```

这些相对路径假设扩展装在 `public/scripts/extensions/third-party/<name>/`。
一旦扩展改放到用户目录（`data/<user>/extensions/<name>/`）或酒馆调整目录结构，就会 404。
本项目在 `event-timer/host/bridge.js` 里只调 `SillyTavern.getContext()`，
并在 `tests/module-tests.mjs` 里加了一条测试，禁止出现这类硬编码路径。

### `getContext()` 返回对象的实际成员（本项目用到的部分）

来自 `public/scripts/st-context.js`（release 与 staging 内容一致）：

```

getCurrentChatId, getRequestHeaders, reloadCurrentChat, renameChat,
saveSettingsDebounced, chatMetadata, saveMetadataDebounced, saveMetadata,
eventSource, eventTypes, event_types,          ← 注意两个都有
addOneMessage, deleteLastMessage, deleteMessage,

sendStreamingRequest, sendGenerationRequest, stopGeneration,

SlashCommandEnumValue, ARGUMENT_TYPE, executeSlashCommandsWithOptions,

...
```

**特别注意**：

- `eventTypes`（camelCase）是新名字，`event_types` 是保留下来的旧别名，**两个都在**。
  本项目用 `ctx.eventTypes ?? ctx.event_types` 兜底。
- **`extension_prompt_types` / `extension_prompt_roles` 这两个枚举不在 context 里。**
  它们的数值直接从源码常量取值（见第 4 节），长期稳定。
- `chat` 与 `chatMetadata` 在切换聊天时会被**整体重新赋值**，
  所以**绝不能缓存 `getContext()` 的返回值**。本项目每次都用 `ctx()` 现取。
- `toastr` 是酒馆页面的全局变量，不在 context 里，需要用 `globalThis.toastr` 取（本项目已做降级）。

## 2. 扩展的目录与加载方式

### 磁盘位置

`src/endpoints/extensions.js` 里：

```js
// 本地（每个用户各自一份）
const userExtensions = readdir(request.user.directories.extensions) ...
    .map(f => ({ type: 'local', name: `third-party/${f}` }));

// 全局（所有用户共享，需要管理员权限）
const globalExtensions = readdir(PUBLIC_DIRECTORIES.globalExtensions) ...
    .map(f => ({ type: 'global', name: `third-party/${f}` }));
```

即：

| 类型 | 磁盘路径 | 加载时被称作 |
| --- | --- | --- |
| 用户扩展（local） | `data/<用户名>/extensions/<文件夹>/` | `third-party/<文件夹>` |
| 全局扩展（global） | `public/scripts/extensions/third-party/<文件夹>/` | `third-party/<文件夹>` |
| 内置扩展（system） | `public/scripts/extensions/<文件夹>/` | `<文件夹>` |

三者最终都以 URL `/scripts/extensions/<上面那个 name>/` 提供给浏览器。
所以**扩展代码不需要知道自己装在哪**，只要用相对路径引自己目录内的文件即可。

### ⚠️ 为什么「放进 `public/scripts/extensions/` 能用，但管理面板里找不到」

这是很常见的困惑，答案在**客户端**的分组逻辑里，跟是不是用 GitHub 链接装的**毫无关系**。

`public/scripts/extensions.js:1068`：

```js
const isExternal = name.startsWith('third-party');
```

`public/scripts/extensions.js:1172`：

```js
extensions.forEach(value => {
    const { isExternal, extensionElement } = value;
    const container = isExternal ? externalContainer : defaultContainer;   // ← 分到两个区块
    container.appendChild(extensionElement);
});
```

而这两个容器的标题（`public/scripts/extensions.js:1141` / `:1150`）：

```js
defaultHeading.textContent  = t`Built-in Extensions:`;    // 内置扩展
externalHeading.textContent = t`Installed Extensions:`;   // 已安装扩展
```

对照第 2 节表格里各目录返回的 `name`：

| 磁盘路径 | 返回的 `name` | `isExternal` | 出现在面板的哪一栏 | 能从面板启停 |
| --- | --- | --- | --- | --- |
| `public/scripts/extensions/<文件夹>/` | `<文件夹>`（**无前缀**） | `false` | **Built-in Extensions（内置扩展）** | ❌ 不能，图标是齿轮，提示「不可删除」 |
| `public/scripts/extensions/third-party/<文件夹>/` | `third-party/<文件夹>` | `true` | **Installed Extensions（已安装扩展）** | ✅ 可以 |
| `data/<用户名>/extensions/<文件夹>/` | `third-party/<文件夹>` | `true` | **Installed Extensions（已安装扩展）** | ✅ 可以 |

**结论**：把扩展直接丢进 `public/scripts/extensions/`，它会被归类为 `system`（内置），
于是出现在「内置扩展」区块里 —— 功能完全正常，只是不在你习惯找的那一栏。
想让它进「已安装扩展」，往下挪一层到 `public/scripts/extensions/third-party/` 即可，
**扩展代码一行都不用改**（两种位置的加载 URL 都是 `/scripts/extensions/third-party/<文件夹>/`）。

顺便一提，`system` 类型的扩展还有两个附带差异：`auto_update` 不会生效
（`public/scripts/extensions.js:1958` 里有 `id.startsWith('third-party')` 的判断），
以及非管理员用户看不到 `global` 类型的扩展（`:1953`）。

### 加载方式：ES 模块

`public/scripts/extensions.js:813`：

```js
function addExtensionScript(name, manifest) {
    const url = `/scripts/extensions/${name}/${manifest.js}`;
    const script = document.createElement('script');
    script.type = 'module';       // ← 关键
    script.src = url;
    document.body.appendChild(script);
}
```

所以：

- **扩展入口是 ES module**，可以放心用 `import` / `export`；
- 扩展目录内的相对 import（`./core/engine.js`）正常工作；
- 不需要打包工具、不需要 `type="module"` 的 package.json；
- Node.js 那边为了让 `.js` 被当 ESM 解析，本项目根目录放了 `{"type":"module"}` 的 package.json，
  **这个文件不要拷进酒馆的扩展目录**（拷了也无害，酒馆不读它）。

### manifest.json

`extensions.js` 实际会读取的字段：

| 字段 | 说明 |
| --- | --- |
| `display_name` | 显示名（排序与 UI 都用它） |
| `loading_order` | 加载顺序，数字越小越早（`sortManifestsByOrder`） |
| `js` | 入口 JS，相对扩展目录 |
| `css` | 样式表，相对扩展目录 |
| `requires` | 需要的 Extras 模块名数组；不是数组只警告不阻断 |
| `optional` | 可选 Extras 模块名数组 |
| `dependencies` | 依赖的其它扩展名数组 |
| `minimum_client_version` | 低于此版本不加载 |
| `hooks` | `{ [hookName]: '导出函数名' }`，见官方文档 |
| `generate_interceptor` | 生成拦截器函数名，见第 6 节 |
| `auto_update` | 第三方扩展是否自动更新 |
| `i18n` | `{ 'zh-cn': 'i18n/zh-cn.json' }`，加载失败只打日志不报错 |

本项目只用了最保守的一组（`display_name` / `loading_order` / `js` / `css` /
`author` / `version` / `homePage` / `minimum_client_version` / 三个空数组）。

## 4. 提示词注入：`setExtensionPrompt`

`public/script.js:8926`：

```js
export function setExtensionPrompt(key, value, position, depth, scan = false,
                                   role = extension_prompt_roles.SYSTEM, filter = null) {
    extension_prompts[key] = {
        value: String(value),
        position: Number(position),
        depth: Number(depth),
        scan: !!scan,
        role: Number(role ?? extension_prompt_roles.SYSTEM),
        filter: filter,
    };
}
```

### 枚举值（`script.js:484` / `494`）

```js
export const extension_prompt_types = {
    NONE: -1,          // 不发给 AI，但仍参与世界书扫描
    IN_PROMPT: 0,      // 插在 story string 之后
    IN_CHAT: 1,        // 按 depth 插入到对话中
    BEFORE_PROMPT: 2,  // 插在 story string 之前
};

export const extension_prompt_roles = {
    SYSTEM: 0,
    USER: 1,
    ASSISTANT: 2,
};
```

### `IN_CHAT` 的实际行为（`script.js:5633-5671`）

```js
const maxDepth = getExtensionPromptMaxDepth();
for (let i = 0; i <= maxDepth; i++) {
    const roles = [SYSTEM, USER, ASSISTANT];        // 同一深度按这个优先级排列
    for (const role of roles) {
        const extensionPrompt = String(await getExtensionPrompt(IN_CHAT, i, '\n', role, false)).trimStart();
        if (extensionPrompt) {
            roleMessages.push({
                name: role === SYSTEM ? '' : (role === USER ? name1 : name2),
                is_user: role === USER,
                mes: extensionPrompt,
                extra: { type: role === SYSTEM ? system_message_types.NARRATOR : null },
            });
        }
    }
    if (roleMessages.length) {
        const depth = isContinue && i === 0 ? 1 : i;
        messages.splice(Math.min(depth + totalInsertedMessages, messages.length), 0, ...roleMessages);
    }
}
```

关键结论：

- **`depth = 0` 表示插在最后一条消息之后**（即你刚发的那条用户消息之后、AI 回复之前）。这正是「注入到下一轮用户输入」想要的位置。
- `role = SYSTEM` 时消息被标记为 **NARRATOR 系统旁白**，不会显示在聊天界面上，只在提示词里。
- 这些消息是**在拼装提示词时临时 splice 进去的**，**不会写回 `chat` 数组**，所以聊天记录干净。
- 同一深度、不同 role 的注入有固定优先级：SYSTEM → USER → ASSISTANT。
- 同名 key 再调一次就是**覆盖**；清空传 `''` 即可。
- 深度上限是 `getExtensionPromptMaxDepth()`（源码里基于 `MAX_INJECTION_DEPTH = 10000` 计算）。

本项目默认 `position = 1 (IN_CHAT)`、`depth = 0`、`role = 0 (SYSTEM)`、`scan = false`，全部可在设置里改。

### 关于 `filter`

第 7 个参数 `filter` 可以是 `() => boolean | Promise<boolean>`，用来做条件注入。
本项目没用它（因为需要在注入时「记账」——记下这个事件提醒过了——用主动计算的时机更可控），
但如果你想让注入完全由酒馆决定时机，这是个好钩子。

## 5. 持久化

### 跟随聊天的数据 → `chatMetadata`

```js
ctx.chatMetadata[KEY] = payload;
ctx.saveMetadataDebounced();
```

- `chatMetadata` 就是模块级的 `chat_metadata`，最终写进 `data/<user>/chats/<角色>/<聊天名>.jsonl` 的元数据里。
- **换聊天时会整体替换**，所以每次都要重新 `getContext()`。
- `updateChatMetadata(newValues, reset)` 会**重新赋值** `chat_metadata`（`script.js:8978`），
  用了它之后旧的引用就失效了 —— 这也是本项目坚持「不缓存 context」的原因之一。

### 全局数据 → `extensionSettings`

```js
ctx.extensionSettings[KEY] = config;
ctx.saveSettingsDebounced();
```

对应 `settings.json` 里的 `extension_settings` 字段。

### 消息级数据

`chat[i].extra` 是每条消息自带的扩展字段（swipe 相关的 `swipe_id` / `swipes` 也在消息上）。
本项目**没有**用消息级存储，因为：

- 改了历史消息 / 换了 swipe 之后，消息级数据容易和正文脱节；
- 本项目选择了「从正文重放得出状态」的路线，只需要存**用户的手动干预**（overlays），
  而那是聊天级而不是消息级的数据。

## 6. 生成拦截器

manifest 里可以写：

```json
{ "generate_interceptor": "myInterceptorFunctionName" }
```

`extensions.js:2033` 会按 `loading_order` 排序后调用这些全局函数。
本项目**没有用**它，原因：

- 拦截器是「同步/异步改最终消息数组」的钩子，而本项目需要的是**在生成前一刻刷新注入并记账**；
- `setExtensionPrompt` 在提示词拼装阶段才被读取，所以只要在生成前把值写好就够了；
- 用 `GENERATION_AFTER_COMMANDS` 事件做这一步更简单，也不依赖 manifest 里的全局函数名。

如果你确实要改最终 prompt 内容，`GENERATE_AFTER_COMBINE_PROMPTS`（payload `{ chat, dryRun }`）
更直接——`chat` 就是拼好的数组，可以直接改。注意判断 `dryRun`，
酒馆在「预览提示词」时也会发这个事件。

## 7. 静默生成（可选 LLM 抽取用）

`script.js:3084`：

export async function generateQuietPrompt({
    quietPrompt = '', quietToLoud = false, skipWIAN = false, quietImage = null,

## 8. 界面挂载点

`public/index.html` 里有两个扩展设置容器：

```html
<div id="extensions_settings"  class="flex1 wide50p">   <!-- 第一列 -->
<div id="extensions_settings2" class="flex1 wide50p">   <!-- 第二列，第三方扩展一般放这里 -->
```

输入框：

```html
<textarea id="send_textarea">
```

本项目：

- 设置抽屉挂到 `#extensions_settings2`（取不到就退回 `#extensions_settings`，
  都取不到就在悬浮面板里给个提示，并支持 `waitForElement` 轮询等待最多 15 秒）；
- 悬浮按钮挂在 `document.body`，用 `position: fixed` + 视口比例坐标，不依赖任何酒馆布局；
- 输入框操作只碰 `#send_textarea`，不碰任何酒馆内部状态。

**本项目刻意没有用 `renderExtensionTemplateAsync` / Handlebars 模板**，
原因有两个：模板文件要多一次网络请求；而且酒馆在 `getContext()` 里已经把
`renderExtensionTemplate` 标记为 deprecated（`registerHelper` 甚至变成了空函数）。
用原生 DOM 拼装更省事，也更好移植到非酒馆宿主。

## 9. 斜杠命令

当前推荐写法（`SlashCommandParser.js:65` / `SlashCommand.js:44`）：

```js
SlashCommandParser.addCommandObject(SlashCommand.fromProps({
    name: 'mycmd',
    aliases: ['mc'],
    helpString: '说明文字',
    returns: '返回值说明',
    namedArgumentList: [],
    unnamedArgumentList: [
        SlashCommandArgument.fromProps({
            description: '参数说明',
            typeList: [ARGUMENT_TYPE.STRING],
            isRequired: true,
        }),
    ],
    callback: (namedArgs, unnamedArgs) => '返回的字符串',
}));
```

要点：

- `registerSlashCommand` 已废弃，用 `SlashCommandParser.addCommandObject`；
- 命令名**不能带斜杠**，`name: 'timer'` 对应 `/timer`；
- 重名会 `console.trace` 警告并拒绝注册（`SlashCommandParser.js:79`）；
- 本项目在 `slash.js` 里把所有构造器都从 `getContext()` 现取，拿不到就静默跳过，
  所以老版本酒馆上只是没有斜杠命令，不会崩。

## 11. 踩过的坑 / 注意事项

1. **不要缓存 `getContext()` 的返回值。**
   `chat`、`chatMetadata` 在换聊天时会被整体替换，缓存下来的是旧对象。
2. **`event_types.CHAT_CHANGED` 的字符串值是 `'chat_id_changed'`**，不是 `'chat_changed'`。永远用枚举取。
3. **`extension_prompt_types` / `extension_prompt_roles` 不在 `getContext()` 里。**
   本项目把它们作为常量写在 `host/bridge.js`。
4. **扩展的入口是 ES module**，但**扩展目录里不要放 package.json 的 `"type": "module"` 依赖**——
   浏览器不看它，别让 Node 的解析规则影响到你对自己代码的判断。
5. **`MESSAGE_RECEIVED` 的 payload 是消息下标，不是消息对象。**
   而且流式输出时这个事件可能**不发**（源码里多处是 `!fromStreaming && emit(...)`），
   所以本项目在 `MESSAGE_RECEIVED` 与 `CHARACTER_MESSAGE_RENDERED` 上都挂了处理，
   并且都有「拿不到下标就取最后一条」的兜底。
6. **切聊天后 `chat` 数组可能还没填好**，本项目在 `CHAT_CHANGED` 里延迟 60ms 再重算。
7. **不要直接改 `chat` 数组来注入内容**（会污染聊天记录、也会触发一连串事件）。
   用 `setExtensionPrompt`。
8. **别 import 酒馆源码的相对路径。** 用 `SillyTavern.getContext()`。
9. 世界书扫描（`scan: true`）会让注入文本参与关键词触发。本项目默认关闭，
   因为提醒文本里含事件名，开着容易意外激活一堆条目。
